## Acceptance Criteria / Issue Body

## Summary

Active-task sync writes multiple `category=project` facts per entity (title, status, next, owner, branch, etc.) and relies on exact `entity` string matching for supersession. Case variants (`humanizer` vs `Humanizer`, `hybrid-memory` vs `Hybrid-Memory`) create separate entity groups, so duplicates never collapse. Closing a task by writing `status=done` does not remove stale status/next facts that lack the matching `entity` case.

## Evidence

**Code:**
- `services/task-ledger-facts.ts:173-179`: `upsertProjectTaskKey` finds previous facts with `facts.filter((f) => f.entity === entity && (f.key ?? "") === key)` — case-sensitive, no normalisation
- `services/task-ledger-facts.ts:52-60`: `rowToRecord` maps entity keys to fields; each variant becomes a separate task row
- `services/task-ledger-facts.ts:85-99`: terminal statuses require exact `done`, `completed`, `cancelled`, `closed`, `abandoned` (lowercased); mixed-case or variant values bypass the filter
- `lifecycle/stage-active-task.ts:40`: reads all non-superseded project facts grouped by exact entity string

**DB evidence (Maeve live facts.db):**
- 5+ separate case-variant entities for the same logical task exist as active rows
- Entity `humanizer` has 98 facts; entity `Humanizer` has separate current facts (not superseded)
- Entity `hybrid-memory` has separate facts from `Hybrid-memory` and `Hybrid-Memory`

## Impact

- Closed/duplicate tasks persist as active rows because supersession only works within exact entity matches.
- Hygiene repeatedly "closes duplicates" that never actually go away.
- Active-task count grows unbounded as case variants accumulate.
- Prompts contain stale tasks that are logically closed but entity-mismatched.

## Acceptance criteria

- When syncing a task, all case-variant variants of the same logical task label must be treated as the same entity.
- Closing a task (writing `status=done`) must supersede all old status/next facts for all case variants of that entity.
- Active-task projection must collapse case variants into one canonical row.
- Terminal status mapping must be case-insensitive.
- Regression test: upsert `Humanizer` as done; verify `humanizer` case-variant rows are also suppressed from active projection.

## Fix direction

- Store a `canonical_label` field on active-task facts; use a normalisation function (trim, lower-case, strip `PR Queue` suffixes) as the canonical key.
- On close, supersede all facts whose `canonical_label` matches, not just exact entity match.
- Add a maintenance migration to set `canonical_label` for existing active-task entities and collapse case-variant duplicates.
